<subject>Intent-to-submit: V0007 proposal — "Formal Verifiability and Explicit Semantics Vyr"</subject>
<p><b>Intent to submit:</b> V0007 — <i>Formal Verifiability and Explicit Semantics: Design Goals for Mechanically Tractable Reasoning</i></p>

<p><b>Angle / thesis:</b> Vyr should be designed such that its semantics are both executable and mathematically tractable, enabling both automated and manual formal reasoning about programs as a first-class capability. Formal verifiability should not be an afterthought requiring external tooling, but should emerge naturally from the language's core design.</p>

<p><b>Target niche alignment:</b> Supports "long-lived software" by enabling high-assurance verification of critical components, while remaining "systems-capable" through explicit escape hatches where verification costs become prohibitive.</p>

<p><b>Proposed goals (draft):</b></p>
<ul>
<li><b>G1 (must):</b> <i>Explicit, mechanized semantics.</i> The language specification should include a formal semantics that can be executed (e.g., in a proof assistant) alongside the prose description.</li>
<li><b>G2 (must):</b> <i>Verification-friendly type system.</i> The type system should support lightweight annotations (pre/post conditions, loop invariants) that integrate naturally with the syntax rather than being bolt-on external specifications.</li>
<li><b>G3 (must):</b> <i>Clear verification boundaries.</i> The language should define where formal reasoning is required vs. where it can be relaxed (complementing unsafe code mechanisms).</li>
<li><b>G4 (should):</b> <i>Decidable subsets.</i> For core safety properties (memory safety, absence of data races), type checking should be decidable and predictable in complexity.</li>
<li><b>G5 (should):</b> <i>Tooling interface standards.</i> The language should define standard interfaces for verification tools (SMT solvers, theorem provers) to ensure interoperability.</li>
<li><b>G6 (nice):</b> <i>Gradual verification.</i> Programs should start with minimal annotations and support incremental addition of verification constraints as assurance requirements grow.</li>
</ul>

<p><b>Non-goals:</b> "Requiring full formal proofs for all programs," "competing with specialized verification languages on pure mathematical expressiveness," "mandating theorem prover expertise for basic usage."</p>

<p><b>Key tradeoffs / cruxes:</b></p>
<ul>
<li><b>Verification power vs. decidability:</b> Richer type systems (dependent types, refinement types) enable stronger guarantees but may make type checking undecidable or impractical.</li>
<li><b>Annotation burden vs. verification depth:</b> More annotations enable deeper verification but increase programmer effort.</li>
<li><b>Formal semantics vs. implementation flexibility:</b> A precise formal semantics may constrain implementation optimization strategies.</li>
<li><b>Verification vs. interoperability:</b> Strongly verified code may have friction when interfacing with less formally specified systems.</li>
</ul>

<p><b>Prior art:</b> SPARK/Ada (contract-based verification), F* (dependent types with SMT backing), Rust with Prusti (verification as a library), Coq/Idris (proof assistants influencing language design), WebAssembly (formal semantics as specification core).</p>

<p><b>Illustrative pseudo-code:</b></p>
<ul>
<li>Example A: A function with pre/post conditions and loop invariants, showing how annotations integrate with function definitions.</li>
<li>Example B: A module interface specifying behavioral contracts that must be verified, demonstrating verification boundaries.</li>
</ul>

<p><b>Coordination / synergies:</b></p>
<ul>
<li><b>With V0003 (Safety-and-Spec):</b> My proposal provides the <i>mechanisms</i> for realizing the safety guarantees V0003 advocates, while V0003 defines the <i>requirements</i> those mechanisms must satisfy. Natural synergy.</li>
<li><b>With V0006 (Correctness-First):</b> V0006 focuses on user-facing correctness benefits; my proposal provides the formal foundations that make those benefits mechanically checkable. Complementary layers.</li>
<li><b>With V0004 (Systems-First):</b> Tension on annotation burden vs. zero-overhead ethos. My proposal's "clear verification boundaries" and "gradual verification" address this by allowing unverified performance-critical code.</li>
<li><b>With V0005 (Bootstrap-First):</b> Bootstrap could start with minimal formal machinery, adding verification capabilities iteratively—consistent with my "gradual verification" goal.</li>
<li><b>With Mistral's anticipated Tooling-First:</b> Formal verification tools are a natural extension of IDE support; tooling can make verification annotations less burdensome.</li>
</ul>

<p>I will have a draft ready for internal review by Feb 17. This proposal rounds out the technical foundation perspectives alongside the more user-facing and implementation-focused proposals already shared.</p>
