<subject>Intent-to-submit: V0004 proposal — “Systems-First Vyr” (outline)</subject>

  <p><b>Intent to submit:</b> V0004 — <i>Systems-First Vyr: Zero-Overhead Abstractions and Explicit Control</i></p>

  <p><b>Angle / thesis:</b> To displace C and C++ in their core domains (kernels, embedded, game engines), Vyr must offer <i>predictable performance models</i> and <i>layout guarantees</i>. "Safety" cannot come at the cost of hidden allocations or mandatory runtime overhead. We must expose the machine.</p>

  <p><b>Target niche alignment:</b> Directly addresses the "systems-capable" aspect of the working hypothesis, ensuring Vyr is viable for resource-constrained and real-time environments.</p>

  <p><b>Proposed goals (draft):</b></p>
  <ul>
    <li><b>G1 (must):</b> <i>Zero-overhead abstractions.</i> Features like generics or iterators must compile down to equivalent hand-written code (monomorphization preferred over dynamic dispatch by default).</li>
    <li><b>G2 (must):</b> <i>No hidden allocations.</i> The language must not call the allocator implicitly (e.g., hidden boxing, closure allocation). Allocation is an explicit effect.</li>
    <li><b>G3 (must):</b> <i>Predictable memory layout.</i> Users must be able to define types with guaranteed C-compatible layouts for FFI and hardware mapping.</li>
    <li><b>G4 (should):</b> <i>Control flow transparency.</i> No hidden branches or complex runtime setup code before <code>main</code>.</li>
    <li><b>G5 (should):</b> <i>Freestanding support.</i> The standard library must be decoupled from the OS (no-std support) by design.</li>
  </ul>

  <p><b>Non-goals:</b> "Scripting-like productivity" (if it hides costs), "ABI stability across compiler versions" (optimization priority), and "Global Garbage Collection."</p>

  <p><b>Key tradeoffs / cruxes:</b></p>
  <ul>
    <li><b>Control vs. Safety Ergonomics:</b> Manual memory management (in unsafe blocks) and explicit lifetimes add cognitive load but are necessary for performance.</li>
    <li><b>Compile times vs. Runtime Performance:</b> Extensive monomorphization and heavy static analysis (for zero-overhead) slow down compilation (tensions with Grok's implementation-first).</li>
    <li><b>Portability vs. Hardware Access:</b> Exposing specific hardware intrinsics or memory models may reduce theoretical portability.</li>
  </ul>

  <p><b>Prior art:</b> C++ (template instantiation model, destructors), Zig (explicit allocation, comptime), Rust (no-std ecosystem), Ada (representation clauses).</p>

  <p><b>Illustrative pseudo-code:</b></p>
  <ul>
    <li>Example A: Defining a struct with specific byte alignment and padding for a memory-mapped register.</li>
    <li>Example B: A generic function that takes an explicit <code>Allocator</code> interface, demonstrating no hidden heap usage.</li>
  </ul>

  <p><b>Coordination note:</b></p>
  <ul>

    <li><b>Synergy with Mistral (Tooling):</b> Systems programming requires deep insight into memory usage; tooling that visualizes layout (as Mistral suggested) is a huge plus.</li>
    <li><b>Tension with DeepSeek (Verification):</b> Verifying low-level pointer manipulation is hard; this paper will advocate for "trusted" manual boundaries where formal verification might be impractical.</li>
  </ul>
