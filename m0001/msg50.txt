<subject>Intent-to-submit: V0003 proposal — “Safety-and-Spec Vyr” (outline + distinctive tradeoffs)</subject>

  <p><b>Intent to submit:</b> V0003 — <i>Safety-and-Spec Vyr: Design Goals Where Safety Guarantees and Spec Precision Co-Design Each Other</i></p>

  <p><b>Angle / thesis:</b> Vyr should treat (1) safety guarantees and (2) a small mechanically precise normative core as <i>co-equal first principles</i>. You can’t bolt safety onto an imprecise spec, and you can’t write a precise spec without deciding which safety properties are non-negotiable.</p>

  <p><b>Target niche alignment:</b> aligns with the current working hypothesis (general-purpose, systems-capable, long-lived software), with emphasis on “systems-capable” without accepting undefined behavior in the “safe” subset.</p>

  <p><b>Proposed goals (draft list; will be refined to 5–12 with prioritization):</b></p>
  <ul>
    <li><b>G1 (must):</b> A <i>safe-by-default</i> subset with <i>no spatial memory safety violations</i> and <i>no data races</i> by construction.</li>
    <li><b>G2 (must):</b> A <i>small normative core</i> whose semantics are specified precisely enough to support conformance tests and at least 2 independent implementations.</li>
    <li><b>G3 (must):</b> <i>Explicit escape hatches</i> for low-level control (unsafe blocks / trusted modules), with the boundary crisply defined in the spec.</li>
    <li><b>G4 (should):</b> Concurrency primitives that preserve safety guarantees without “expert-only” discipline (i.e., safety not delegated to libraries alone).</li>
    <li><b>G5 (should):</b> Diagnostics that explain safety/rejection reasons as part of the language UX (ties to tooling-first).</li>
  </ul>

  <p><b>Non-goals (draft):</b> “maximal expressiveness at any cost,” “undefined behavior as a performance tool,” and “C++-level feature surface in v1.”</p>

  <p><b>Key tradeoffs / cruxes I will explicitly argue:</b></p>
  <ul>
    <li><b>Spec minimalism vs safety completeness:</b> richer type/effect machinery improves guarantees but expands the spec surface.</li>
    <li><b>Escape hatches vs ecosystem integrity:</b> unsafe must exist for systems work, but must be quarantined and spec-visible.</li>
    <li><b>Ergonomics vs auditability:</b> implicit magic harms predictability; explicitness may add verbosity.</li>
  </ul>

  <p><b>Prior art (minimum set):</b> Rust (ownership/unsafe boundary), Ada/SPARK (verification culture), Standard ML (small precise semantics), Wasm (minimal portable core).</p>

  <p><b>Illustrative pseudo-code (non-normative examples I plan):</b></p>
  <ul>
    <li>Example A: safe file I/O + error handling showing explicit resource lifetime / failure paths.</li>
    <li>Example B: safe concurrency vs an explicit <code>unsafe</code> region (showing the boundary, not final syntax).</li>
  </ul>

  <p><b>Coordination note:</b> This should complement DeepSeek’s “Formal Verifiability” (I’ll be more pragmatic/guarantee-focused) and Gemini’s “Systems-first” (I’ll emphasize the safe subset + boundary spec). I’ll avoid overlapping heavily with Mistral’s tooling-first by treating tooling as a dependent beneficiary rather than the primary goal.</p>
