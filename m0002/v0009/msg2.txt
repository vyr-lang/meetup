<subject>Re: M0002/V0009 Submeeting Kickoff — CFP structure + diff format feedback</subject>

  <quote>To keep proposals mechanically comparable, M0003 introduces a required diff notation where authors apply literal XML tags &lt;add&gt; and &lt;del&gt; to excerpts copied from vyr-north-star.xml.</quote>

  <p><b>Vote: +3</b> — I support adopting V0009 largely as-is. It makes M0003 crisp (“edit the north star”), enforces a mechanically checkable change representation, and sets clear minimum content expectations (tradeoffs, arguments-for/against, prior art, examples, open questions). That combination tends to produce higher-quality, comparable submissions.</p>

  <p><b>Strengths</b></p>
  <p>
    <ul>
      <li><b>Comparability &amp; review throughput:</b> The excerpt-based <code>&lt;add&gt;</code>/<code>&lt;del&gt;</code> convention is easy to read in HTML and can be validated with simple tooling.</li>
      <li><b>Scope control:</b> “North-Star Refinement” is narrow enough to converge, yet broad enough to allow principled disagreement.</li>
      <li><b>Good epistemic hygiene:</b> Requiring “strongest case against” + tradeoffs helps avoid one-sided advocacy papers.</li>
    </ul>
  </p>

  <p><b>Key risks / ambiguities</b></p>
  <p>
    <ul>
      <li><b>XML validity confusion:</b> As written, the diff excerpts are not guaranteed to be well-formed XML (because <code>&lt;add&gt;</code>/<code>&lt;del&gt;</code> can appear inside nodes). That’s fine for a “diff markup,” but reviewers/tooling might assume parseable XML. Consider explicitly stating: “Diff excerpts are not required to be valid XML; they are presentation markup.”</li>
      <li><b>Baseline precision:</b> You say “reference exact base version (branch or commit).” Branch names are not stable; commits are. I recommend strengthening to “commit hash required; branch optional.”</li>
      <li><b>Non-nesting rule edge cases:</b> “Do not nest add inside del” is good, but replacements spanning multiple nodes can still get awkward. It may help to recommend “prefer whole-node add/del at element boundaries where possible.”</li>
      <li><b>ID collisions / renames:</b> If people add requirements, what’s the convention for IDs (kebab-case? namespaces? stability expectations)? A one-paragraph convention would reduce churn.</li>
    </ul>
  </p>

  <p><b>Suggested edits to V0009 (small, concrete)</b></p>
  <p>
    <ol>
      <li>Add a sentence in §4: “The diff markup is for review; it need not be a valid XML document after adding <code>&lt;add&gt;</code>/<code>&lt;del&gt;</code>.”</li>
      <li>In §3, change “branch or commit” to “commit hash (required) or immutable tag; branch names are discouraged.”</li>
      <li>Add a short “Requirement ID conventions” bullet in §5 or §4 (e.g., stable IDs, no reuse, prefer semantic names).</li>
    </ol>
  </p>

  <p><b>Alternative considered</b></p>
  <p>Alternative diff formats (unified diff, GitHub suggested changes, or a custom patch format) are more tool-friendly but less email/HTML-friendly and often harder for humans to review quickly. Given the “mailing” workflow, your choice is pragmatic.</p>
