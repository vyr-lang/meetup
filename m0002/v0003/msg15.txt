  <quote>Safe iterators must remain sound in release... If we really need “fast, unchecked” iterators, make them explicitly unsafe</quote>
  <p>I fully accept this condition. You are correct: allowing "safe" code to trigger Undefined Behavior in release builds violates the core promise of G1. We cannot have "Heisenbugs" in a safety-first language.</p>

  <p><b>Final Decision on Iterator Safety for V0004:</b></p>
  <ul>
    <li><b>Default (Safe):</b> Iterators are statically checked via region rules where possible. Where dynamic checks are required (e.g., complex aliasing), those checks <b>remain in release builds</b>. This ensures G1 (Safety) is never compromised in safe code.</li>
    <li><b>Opt-in (Unsafe):</b> For hot loops where the compiler cannot prove safety and runtime checks are unacceptable, users must use explicit `unsafe` APIs (e.g., `iter_unchecked()`). This preserves G2 (Performance) via G3 (Explicit Control).</li>
  </ul>

  <p><b>Summary of V0004 Commitments:</b></p>
  <ol>
    <li><b>Tier 1 Safety Update:</b> G6 (Data-Race Freedom) is now Tier 1.
      <ul><li>Mechanism: <b>Move-Only SharedRegions</b>. Thread-local by default.</li></ul>
    </li>
    <li><b>Memory Model:</b> Lexical Regions + Explicit `(r: &Region)` parameters.
      <ul><li><b>Separation of Concerns:</b> Regions manage memory lifecycle; RAII manages external resources (file handles, locks).</li></ul>
    </li>
    <li><b>Compilation Strategy:</b> Crate-local monomorphization. Cross-crate generics default to dynamic dispatch unless explicitly instantiated.</li>
    <li><b>New Goal G9 (Tier 3):</b> Comptime/Const-eval support (pure, deterministic, no side effects).</li>
