<h2>1. Abstract</h2>

<p>Vyr should be a language where the toolchain is not an afterthought but a first-class citizen, serving the ultimate goals of developer productivity, cognitive clarity, and correctness. This revised proposal outlines durable language invariants that enable exceptional tooling, drawing inspiration from modern ecosystems while addressing their pain points. These invariants target developers building complex software, ensuring "zero-config" productivity gains through verifiable properties like refactor safety and partial-program analysis.</p>

<h2>2. Tooling-Enabling Language Invariants</h2>

<p>The core of this proposal is a set of testable language invariants that guarantee tooling robustness. These are spec-level requirements, verifiable via conformance tests. Aspirational benchmarks (e.g., performance metrics) are moved to Appendix A.</p>

<ol>
<li><strong>Deterministic Parse and Recovery Contract:</strong> Given any byte sequence, the parser must produce a best-effort CST/AST plus a structured error set; recovery must preserve token order and provide stable node IDs where feasible.</li>
<li><strong>Fully Specified Name Resolution:</strong> Resolution rules must be complete, deterministic, and defined for partially missing symbols (e.g., “unknown symbol” nodes with provenance).</li>
<li><strong>Typed Semantic Graph with Bounded-Unknown Semantics:</strong> The type system must support holes/unknowns so analysis can proceed under errors. Unknowns propagate locally within an expression/function body but are bounded at named boundaries (function signatures, module exports), producing best-effort symbol shapes without invalidating unrelated analysis.</li>
<li><strong>Refactorability Invariants:</strong> Define a small set of semantics-preserving refactors (e.g., rename, move, extract) with checkable preconditions from the semantic graph; tools refuse if preconditions fail.</li>
<li><strong>Stable Serialized Standard Object Model (SOM):</strong> A versioned, forward-compatible semantic graph format (unknown fields preserved) with explicit schema evolution rules.</li>
<li><strong>Structured Diagnostics Contract:</strong> Every diagnostic includes span(s), primary code, causal chain links, optional fix-it edits, and machine-readable metadata.</li>
<li><strong>Grammar Stratification:</strong> Parsing and recovery are independent of name/type resolution; disambiguation relies on syntax alone or limited token lookahead, never the type checker.</li>
<li><strong>Syntactic Regularity and Locality of Reference:</strong> The grammar prioritizes predictability, strict local resolution, and graceful error recovery to minimize "spooky action at a distance."</li>
</ol>

<h2>3. Prioritization</h2>

<ul>
<li><strong>Must-Have (All Invariants):</strong> These form the foundation; without them, Vyr cannot deliver on tooling-first promises.</li>
<li><strong>Should-Have (Benchmark Aspirations in Appendix A):</strong> Targets for reference implementations to differentiate Vyr.</li>
</ul>

<h2>4. Non-Goals</h2>

<ol>
<li><strong>Runtime Tooling Dominance:</strong> No prioritization of dynamic introspection over static guarantees.</li>
<li><strong>Universal Tool Agnosticism:</strong> Hooks must be structured to prevent fragility.</li>
<li><strong>Batteries-Included Tool Suite:</strong> Focus on primitives for ecosystem tools, not shipping a full IDE.</li>
<li><strong>Legacy Tool Compatibility:</strong> Targets forward-looking stacks, no pre-2020 concessions.</li>
<li><strong>Zero-Overhead Tooling:</strong> Acceptable metadata emission for velocity gains.</li>
<li><strong>Solo-Developer Exclusion:</strong> Optimizes for team/enterprise but must not preclude lightweight single-file usage or REPL experimentation.</li>
</ol>

<h2>5. Rationale</h2>

<p>Tooling is a means to developer productivity and correctness, not an end. These invariants ensure a simple mental model is preserved at scale. Vyr assumes tool-augmented developers, emphasizing easy onboarding and depth for complex codebases. Revisions prioritize cognitive clarity: if a trade-off arises between tool-friendliness and mental simplicity, choose the latter.</p>

<h2>6. Tradeoffs</h2>

<ul>
<li><strong>Compile-Time Overhead:</strong> Metadata may inflate sizes; mitigated by flags.</li>
<li><strong>Language Complexity:</strong> Invariants add spec steepness but yield long-term gains.</li>
<li><strong>Runtime Purity:</strong> Static biases may concede perf in dynamic scenarios.</li>
<li><strong>Ecosystem Lock-In:</strong> Schemas risk fragmentation; offset by versioning.</li>
</ul>
