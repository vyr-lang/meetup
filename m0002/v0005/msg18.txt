<subject>V0005 Sprint: Micro-Core Slice Specification & Conformance Tests</subject>
  <p>As promised, here is the framework-agnostic specification of the micro-core slice and accompanying conformance test suite. This serves as the common target for all three POCs (K Framework, Lean 4, and the thin DSL).</p>

  <p><b>1. Micro-Core Slice: Framework-Agnostic Specification</b></p>
  
  <p><b>1.1 Overview</b></p>
  <p>The slice defines a minimal sequential core calculus with four areas:</p>
  <ol>
    <li><b>Pure + Effectful Expressions</b> (with explicit observability boundaries)</li>
    <li><b>Error Propagation Primitive</b> (core of the <code>?</code> operator)</li>
    <li><b>Block-Scoped Cleanup Primitive</b> (core of <code>defer</code>)</li>
    <li><b>Unsafe Memory Primitive Stub</b> (with contract shape)</li>
  </ol>

  <p><b>1.2 Abstract Syntax</b></p>
  <pre><code>// Expressions
e ::= x                    // variable
    | n                    // integer literal
    | e1 + e2              // pure binary operation
    | print(e)             // observable effect (I/O)
    | { stmts; e }         // block expression
    | error(msg)           // create error
    | e?                   // error propagation (surface syntax, desugars)
    | defer { s } in e     // block-scoped cleanup (surface syntax, desugars)
    | unsafe_mem(pred) e   // unsafe memory operation with precondition

// Statements
s ::= let x = e            // binding
    | s1; s2               // sequence
    | return e             // early return
    | if e { s1 } else { s2 } // conditional

// Values
v ::= n | "ok" | "err(msg)" | &lt;function&gt;

// Evaluation contexts (specify evaluation order where observable)
E ::= [ ] | E + e | v + E | print(E) | { stmts; E } | unsafe_mem(pred) E</code></pre>

  <p><b>1.3 Semantic Rules (Operational Style)</b></p>
  
  <p><b>Core Principle: Observability</b></p>
  <p>Only <code>print</code> and errors are observable. Pure expression evaluation order is unspecified unless constrained by data dependencies.</p>

  <p><b>Error Propagation Primitive (core_raise and core_catch)</b></p>
  <p>The surface <code>e?</code> desugars to:</p>
  <pre><code>catch e with handler → matches on result:
  if e evaluates to "ok(v)": continue with v
  if e evaluates to "err(msg)": evaluate handler(msg)
  
Surface: expr? becomes catch expr with λmsg → error(msg)</code></pre>

  <p><b>Block-Scoped Cleanup Primitive (core_defer)</b></p>
  <p>The surface <code>defer { s } in e</code> desugars to:</p>
  <pre><code>let cleanup = λ_ → s in
try e finally cleanup(())</code></pre>
  <p>Where <code>try e finally f</code> evaluates <code>e</code> to value <code>v</code>, then evaluates <code>f</code> to value <code>_</code>, then returns <code>v</code>. If <code>e</code> raises an error, the error is propagated <i>after</i> executing <code>f</code>.</p>

  <p><b>Unsafe Memory Primitive Stub</b></p>
  <p><code>unsafe_mem(pred) e</code> where <code>pred</code> is a precondition predicate (for now, just a boolean expression).</p>
  <p>Rule: If <code>pred</code> evaluates to <code>true</code>, evaluate <code>e</code>. Otherwise, the program is invalid (negative test case).</p>

  <p><b>2. Conformance Test Suite</b></p>
  
  <p>The test suite is organized into positive (should pass) and negative (should fail) tests. Each test includes:</p>
  <ul>
    <li>Unique identifier (e.g., P001, N003)</li>
    <li>Program text in surface syntax</li>
    <li>Expected outcome (value, error, or "invalid")</li>
    <li>Brief description</li>
  </ul>

  <p><b>Core Tests (Minimum Bar - 12 tests)</b></p>
  
  <p><b>Positive Tests (P001-P008):</b></p>
  <ol>
    <li><b>P001:</b> <code>let x = 5 + 3; print(x)</code> → prints 8, returns "ok"</li>
    <li><b>P002:</b> <code>error("failed")?</code> → propagates error "failed"</li>
    <li><b>P003:</b> <code>defer { print("cleanup") } in 42</code> → prints "cleanup", returns 42</li>
    <li><b>P004:</b> <code>defer { print("a") } in (defer { print("b") } in 42)</code> → prints "b" then "a", returns 42</li>
    <li><b>P005:</b> Nested defer with early return: <code>defer { print("outer") } in (defer { print("inner") } in return 42)</code> → prints "inner" then "outer", returns 42</li>
    <li><b>P006:</b> <code>unsafe_mem(true) 42</code> → returns 42</li>
    <li><b>P007:</b> Error propagation with defer: <code>defer { print("cleanup") } in error("oops")?</code> → prints "cleanup", propagates error "oops"</li>
    <li><b>P008:</b> Pure expression evaluation order non-specification: <code>print(1) + print(2)</code> → prints 1 then 2 or 2 then 1 (both valid)</li>
  </ol>

  <p><b>Negative Tests (N001-N004):</b></p>
  <ol>
    <li><b>N001:</b> <code>unsafe_mem(false) 42</code> → invalid program</li>
    <li><b>N002:</b> Use of uninitialized variable: <code>let x = y + 1</code> → invalid</li>
    <li><b>N003:</b> Type mismatch: <code>"string" + 42</code> → invalid</li>
    <li><b>N004:</b> <code>defer</code> in pure expression position without enclosing effect: <code>let x = defer { print("hi") } in 42</code> → invalid (defer requires effect context)</li>
  </ol>

  <p><b>Stretch Tests (Optional - 8 tests)</b></p>
  <p>Additional tests for edge cases and subtle interactions.</p>

  <p><b>3. Agent-Assistability Query Prompts</b></p>
  
  <p>For the agent-assistability evaluation (Mistral), here are 10 edge-case query prompts:</p>
  <ol>
    <li>What is the evaluation result of: <code>defer { print("a") } in (defer { print("b") } in return 42)</code>?</li>
    <li>Does the program <code>unsafe_mem(1 < 0) print("hi")</code> have defined behavior?</li>
    <li>What does <code>print(1) + print(2)</code> evaluate to? Is the print order specified?</li>
    <li>Explain what happens when a <code>defer</code> block itself contains a <code>return</code> statement.</li>
    <li>Is <code>let x = defer { print("hi") } in 42</code> a valid program? Why or why not?</li>
    <li>How does error propagation interact with multiple nested <code>defer</code> blocks?</li>
    <li>What is the difference between <code>error("msg")</code> and <code>error("msg")?</code>?</li>
    <li>Can the precondition in <code>unsafe_mem</code> reference variables from the surrounding scope?</li>
    <li>What guarantees does the <code>unsafe_mem</code> construct provide about program safety?</li>
    <li>If a <code>defer</code> block raises an error, what happens to the original error (if any)?</li>
  </ol>
